# 技術選定の記録

このアプリで「何を選んだか」と、同じくらい重要な「**何を選ばなかったか**」を残す文書。

選定時点の判断なので、前提が変われば結論も変わる。各項目に「**見直す条件**」を書いてあるので、
その条件に当てはまったら再検討してよい。現行の画面仕様は [`spec.md`](spec.md)、
モジュール構成は [`architecture.drawio`](architecture.drawio) を参照。

---

## 0. 前提

判断の土台になっている条件。これが変わると以下の結論の多くが変わる。

| 項目 | 内容 |
|---|---|
| 利用者 | 個人の学習用。同時アクセスは1〜数人 |
| データ量 | 1ユーザーあたり数百〜数千問を想定 |
| チーム規模 | 1人（将来的に数人） |
| 運用 | 常時稼働のサーバーは前提にしない |
| 目的 | 学習アプリとして成立させること、および設計の訓練 |

**「小さく作って、構造だけは後から育てられるようにする」**が全体の方針。
規模を先回りして大きな仕組みを入れることはしない。

## 1. アーキテクチャ

### 選んだもの: クリーンアーキテクチャ（の簡略版）＋ モジュラーモノリス

`domain` / `use-cases` / `infrastructure` / `presentation` / `api` の層を持ち、
依存は常に内側（domain）へ向かう。業務上の関心事ごとに `modules/` を分ける。

**理由**

1. **差し替えが起きることが分かっていた。** 本文抽出もクイズ生成も、最初はモックで作って
   後から実物に繋ぐ計画だった。ポートとアダプタで切っておけば、`container.ts` の
   bind 先を変えるだけで済む。実際この想定どおりに動いている（env での切り替えを実装済み）
2. **業務ルールをテストしたかった。** 「順番どおりにしか回答できない」「最後に答えて
   間違えたままなら復習対象」といった判断を、DB や HTTP を立てずにテストできる
3. **設計の訓練という目的が明示されていた。** 規模だけで言えば過剰だが、
   それ自体が目的に含まれている

### 選ばなかったもの

#### レイヤードアーキテクチャ（controllers / services / models）

**不採用の理由**: 技術レイヤーで横に切ると、1つの機能を直すのに3ディレクトリを
往復することになる。また `services/` が肥大化しやすく、業務ルールがどこにあるか
分からなくなる。本プロジェクトは「復習の仕様」のようにまとまった業務ルールを持つため、
縦に切るほうが変更が局所化する。

**見直す条件**: 業務ルールがほぼ無く、CRUD が中心になった場合。

#### トランザクションスクリプト（素朴な手続き型）

**不採用の理由**: 規模的には最も素直で、実際この規模なら成立する。
ただし「エンティティがドメインの挙動を持つ」ことを設計目標に置いたため採らなかった。
採用していれば `Attempt` や `Quiz` の不変条件は各所の if 文に散っていたはず。

**見直す条件**: 業務ルールが増えない見通しが立ち、層の維持コストが上回ったとき。

#### マイクロサービス

**不採用の理由**: 利用者が個人で、モジュール間の通信が HTTP になる利点が無い。
デプロイ単位が増えるぶん運用が重くなるだけ。
**モジュラーモノリスは「将来分割したくなったときの準備」**でもあり、
モジュール境界さえ保っておけば切り出しは後から可能。

**見直す条件**: 特定モジュールだけ負荷やスケール要件が突出したとき。

#### イベント駆動 / CQRS

**不採用の理由**: 書き込みと読み取りのモデルを分ける必要が出るほど、
読み取りが複雑でも高負荷でもない。
ただし `analytics` は実質的に読み取り専用の集計ビューであり、
**CQRS の読み取り側に近い位置づけ**になっている（下記 6 を参照）。

**見直す条件**: 集計が重くなり、書き込みと分離した読み取りモデルが必要になったとき。

## 2. フレームワーク: Next.js 16（App Router）

**選んだ理由**

1. **サーバーとクライアントを1つのコードベースで書ける。** React Server Components で
   DB アクセスを含む描画をサーバー側に置けるため、API 層を別途立てなくてよい
2. **Server Actions でフォーム送信が完結する。** REST エンドポイントを定義せずに
   「クライアントから関数を呼ぶ」形で書ける
3. **正解を隠す設計と相性が良い。** 出題画面では正解と解説をクライアントに渡さない
   方針を採っており、RSC なら「そもそも送らない」が自然に書ける

**代償**

- サーバー／クライアント境界の規約が必要になった。`'use client'` から
  `index.ts` を import すると Prisma がブラウザ側に引きずられてビルドが壊れる。
  これは**実際に一度踏んでいる**。対策として公開口を3つ（`index.ts` / `actions.ts` /
  `components/`）に分ける規約を敷いた
- フレームワークへの結合度は高い。Next.js を捨てるなら `app/` と `presentation/` は
  書き直しになる（ただし `domain/` と `use-cases/` は影響を受けない）

### 選ばなかったもの

| 候補 | 不採用の理由 |
|---|---|
| **SPA + 別API（Vite + Express / NestJS）** | リポジトリとデプロイ先が2つになる。型の共有に別途仕組みが要る。個人開発では管理コストが利点を上回る |
| **Remix / React Router** | 要件を満たすが、RSC での「正解を送らない」実装は Next.js のほうが素直。選定時点で優位性が見出せなかった |
| **Rails / Laravel** | サーバーサイドレンダリングの完成度は高いが、TypeScript で型を通したかった |

**見直す条件**: モバイルアプリなど Web 以外のクライアントが必要になったとき。
その場合は `use-cases/` の上に HTTP API 層を足す（`domain/` は変更不要）。

## 3. データベース: SQLite + Prisma 7

**SQLite を選んだ理由**

1. 個人利用で同時書き込みがほぼ無い。SQLite の書き込みロックが問題にならない
2. ファイル1つで完結する。開発環境の構築に DB サーバーの起動が要らない
3. 数千件規模では性能上の制約にならない

**Prisma を選んだ理由**

1. スキーマからの型生成が強力。`schema.prisma` を変えると型エラーで
   修正箇所が洗い出される
2. マイグレーションの管理が仕組みとして用意されている
3. driver adapter（`@prisma/adapter-better-sqlite3`）で SQLite を素直に使える

**代償と割り切り**

- SQLite には配列型が無いため、選択肢（`string[]`）を **JSON 文字列として保存**している。
  変換は `infrastructure/` に閉じ込め、ドメインは `string[]` だけを扱う
- PostgreSQL へ移るときはマイグレーションの書き直しが必要。ただし
  リポジトリ実装（`infrastructure/`）の中で閉じるため、ドメインとユースケースは影響を受けない

### 選ばなかったもの

| 候補 | 不採用の理由 |
|---|---|
| **PostgreSQL** | 要件に対して運用コストが見合わない。必要になってから移る（上記のとおり移行範囲は限定的） |
| **Drizzle ORM** | SQL に近く軽量だが、マイグレーション管理と型生成の成熟度で Prisma を採った |
| **TypeORM** | デコレータでエンティティを定義する方式が、ドメインエンティティを ORM から独立させる方針と衝突する |
| **素の SQL（better-sqlite3 直接）** | 型が手書きになる。スキーマ変更時の追従を人力でやることになる |

**見直す条件**: 同時書き込みが発生する、またはデータ量が数十万件規模になったとき。

## 4. DI: InversifyJS

**選んだ理由**

ポートと実装の結び付けを `container.ts` の1箇所に集約し、
ユースケースが実装クラスを知らない状態を保つため。

**代償**

- `reflect-metadata` とデコレータが必要で、記述が増える
- TypeScript のインターフェースは実行時に消えるため、
  `Symbol.for()` を識別子にする一手間がかかる

### 選ばなかったもの

#### 手書きのコンポジションルート（DI ライブラリなし）

```ts
// こう書けば済む、という案
const generator = new MockQuizGenerator();
const generateQuizzes = new GenerateQuizzesUseCase(generator);
```

**不採用の理由**: 依存が3段以上になると組み立ての記述が長くなり、
どこで何を new しているか追いにくくなる。

**ただしこれは判断が分かれる。** 現在の bind は22個で、手書きでも十分管理できる規模。
ライブラリを外すなら今が最後の機会に近い。

**見直す条件**: デコレータの記述量が負担になった、または
モジュールが増えて起動時の import 連鎖が重くなったとき。

#### tsyringe / TypeDI

**不採用の理由**: 要件は満たすが、`ContainerModule` 単位で
バインディングをまとめられる点で InversifyJS を採った。
モジュールごとに `container.ts` を持つ構成と噛み合う。

## 5. UI: Tailwind CSS 4 + shadcn/ui + Radix UI

**選んだ理由**

1. **shadcn/ui はライブラリではなくコードを配置する方式。** 生成されたコンポーネントが
   リポジトリに入るため、挙動を変えたいときに本体を書き換えられる
2. **Radix UI がアクセシビリティを引き受ける。** ドロップダウンのキーボード操作や
   ARIA 属性を自前で作ると漏れる
3. Tailwind はクラス名の設計を省略できる。デザイナー不在の個人開発に向く

**構成**

Atomic Design に沿って `components/` を分けている。

```
ui/         shadcn/ui の生成物。手を入れない
atoms/      ui/ の再エクスポート層（差し替え点）
molecules/  atom を組み合わせた小部品
organisms/  画面共通のシェル（ヘッダー、ユーザーメニュー）
```

`atoms/` を挟んでいるのは、shadcn/ui の生成物を再生成しても
アプリ側の import を壊さないため。

### 選ばなかったもの

| 候補 | 不採用の理由 |
|---|---|
| **MUI / Chakra UI** | デザインの方向性がライブラリに固定される。カスタマイズは可能だが、個人開発では設定に時間を取られる |
| **CSS Modules / styled-components** | クラス名やコンポーネント名の設計が必要になる。Tailwind なら省略できる |
| **ヘッドレス UI を使わず自作** | ドロップダウンのキーボード操作・フォーカストラップ・ARIA を自前実装すると確実に漏れる |

## 6. 設計上の個別判断

### `analytics` が他モジュールのテーブルを直接読む

**判断**: 意図的な例外として認める。ただし**書き込みは一切しない**。

**理由**: ダッシュボードは「件数を数える」処理の集まりで、他モジュールのユースケースを
1件ずつ呼ぶと往復が増える。読み取り専用の集計ビューとして割り切った。

**代償**: 他モジュールのテーブル構造に依存する。スキーマ変更時に
`analytics` も追従が必要。

**見直す条件**: 集計が複雑化したとき。その場合は CQRS の読み取りモデルを
明示的に立てる（専用のビューまたはテーブルを持つ）。

### 復習対象の判定を「最後に答えて間違えたまま」だけにする

**判断**: 単純な定義を維持する。間隔反復（SRS）は入れない。

**理由**: 弱点は認識している（まぐれ正解すると二度と出てこない）。
しかし SRS を入れると正解回数・次回出題日・難易度係数をスキーマに持つ必要があり、
学習アプリとして成立させる段階では過剰と判断した。

**見直す条件**: 実際に使ってみて「もう解けるのに出てくる」「解けないのに出てこない」が
頻発したとき。`lastAnsweredAt` は既にあるので、経過日数を条件に足すだけなら
スキーマ変更なしで実現できる。

### セッション管理を自前で実装する

**判断**: Auth.js などのライブラリを使わず、scrypt とランダムトークンで自前実装した。

**理由**: 要件がメールアドレスとパスワードのみで、OAuth を使わない方針が確定していた。
ライブラリの設定を理解するコストと、自前実装のコストが見合うと判断した。

**担保していること**

- パスワードは scrypt のハッシュのみ保存。パラメータを同梱し、将来コストを上げても照合できる
- セッショントークンは **SHA-256 ハッシュのみ** DB に保存。平文は保存しない
- ログイン失敗時に「アドレスが存在しない」と「パスワードが違う」を区別しない
- ユーザーが存在しない場合もハッシュ照合と同等の時間をかける

**見直す条件**: OAuth や多要素認証を追加するとき。
その時点で Auth.js への移行を検討する（`User` から `Credential` を分離する準備が前提）。

# QuizStack 仕様書

記事のURLから4択クイズを生成し、1問ずつ出題して採点するアプリケーション。

この文書が**現行仕様の正**。仕様を変更したら必ずここを更新する。
`init.md` はフェーズ1の実装指示書として凍結してあり、現状とは一致しない。

---

## 1. 全体像

### 画面と遷移

```
未ログイン
  /login  ──────┐
  /signup ──────┤ 認証に成功
                ▼
ログイン済み
  /               ホーム（URL入力）
    ↓ 送信
  /generating     ローディング（ここで生成処理を実行）
    ↓ 完了で自動遷移
  /attempt/[id]           出題（1問ずつ）
    ↓ 全問回答
  /attempt/[id]/result    結果（スコアと全問の振り返り）
    │
    └→ 間違えた問題を復習 ──┐
                            │
  /dashboard      ダッシュボード（学習状況・各一覧への入口）
    ├→ /quizzes   問題一覧（作った問題すべて。絞り込み・選んで解き直す）
    │    └→ 選んだ問題を解く ──┤
    └→ /review    復習待ち一覧（間違えたままの問題）
         └→ 復習を始める ──────┤
                                ▼
                          /attempt/[id]（出題へ合流）
```

出題・回答・採点はどの入口から来ても同じ `/attempt/[id]` で行う。
違いは「何を出題対象にするか」だけで、解いている間の画面と操作は変わらない。

### ルートグループ

| グループ | 対象 | 認証 |
|---|---|---|
| `(app)` | `/` `/generating` `/attempt/*` `/dashboard` `/quizzes` `/review` | 必須。未ログインは `/login` へ |
| `(auth)` | `/login` `/signup` | 不要。ログイン済みは `/` へ |

`(app)` のレイアウトは共通ヘッダーを表示する。`(auth)` にヘッダーはない。

### モジュール

| モジュール | 責務 | 現在の実装 |
|---|---|---|
| `user` | 登録・認証・セッション | 本実装（Prisma + SQLite） |
| `content-extraction` | URLから本文を抽出 | **モック**（ネットワーク未使用） |
| `quiz-generation` | 抽出結果からクイズを生成 | **モック**（3問固定・遅延あり） |
| `quiz-session` | 出題・回答・採点 | ロジックは本実装、保存は**メモリ** |
| `analytics` | 学習状況の集計（ダッシュボード） | **モック**（固定データ） |
| `quiz-catalog` | クイズの保管・検索・正誤状態の管理 | **未着手** |

`quiz-catalog` は復習（第5章）と問題一覧の前提になる。
「生成する人」ではなく「保管し、条件で検索させる人」という位置づけで、
`Quiz.lastIsCorrect` の更新もこのモジュールが担う。

## 2. 認証・認可

### 認証方式

メールアドレスとパスワード。OAuth は使わない。

ユーザーが持つ情報は **ユーザー名・メールアドレス・パスワード** のみ。

### 登録（`/signup`）

- 入力: ユーザー名 / メールアドレス / パスワード
- パスワードは **8文字以上128文字以下**、空白のみは不可
- メールアドレスは正規化（前後空白除去・小文字化）してから一意性を判定する
- 登録に成功するとそのままログイン状態になる
- 既に登録済みのアドレスは「このメールアドレスはすでに登録されています」

### ログイン（`/login`）

- 失敗理由は **「アドレスが存在しない」と「パスワードが違う」を区別しない**。
  区別すると登録済みアドレスの存在を総当たりで確認できてしまうため
- ユーザーが存在しない場合もハッシュ照合と同等の時間をかける（応答時間から推測させない）

### パスワードの保存

- Node 標準の **scrypt**。ソルトはユーザーごとにランダム
- 保存形式 `scrypt$N$r$p$<salt>$<hash>`。パラメータを同梱しているため、
  将来コストを引き上げても既存ハッシュを照合できる
- 照合は `timingSafeEqual`

### セッション

- ログインのたびに新しいトークンを発行する（セッション固定攻撃の防止）
- DBに保存するのは **トークンの SHA-256 ハッシュのみ**。平文は保存しない
- 有効期間 30日
- Cookie: `httpOnly` / `sameSite=lax` / 本番のみ `secure` / `path=/`
- ログアウト時はサーバー側のセッションを削除したうえで Cookie も削除する

### 認可

- `(app)` のレイアウトでログインを確認する。ただし**これは認可の境界ではない**。
  画面を出さないための措置であり、データに触れる各所（`api/` と Server Action）が
  あらためて所有者を確認する
- **Attempt は開始したユーザーのもの**。他人の挑戦は閲覧も回答もできない
- 他人の挑戦に対しては「権限がありません」ではなく **「見つかりません」** を返す。
  区別するとIDの総当たりで他人の挑戦の実在を確認できてしまうため
- 回答者はクライアントの申告ではなく**セッションから決める**

## 3. クイズの生成と出題

### ホーム（`/`）

- URL入力フィールドのみ。問題数の選択UIはない（常に3問固定のため）
- 送信すると `/generating?url=...` へ**ルート遷移**する（同一画面での状態切り替えはしない）

### 本文抽出（`content-extraction`）

現在はモックだが、モック・本実装のどちらでも次のドメインルールが適用される。

- **https 以外のURLは受け付けない**
- トラッキングパラメータ（`utm_*` `fbclid` など）を除去し、フラグメントを削除する
- 本文が **200文字未満**ならクイズを作れないものとして拒否する
- 本実装ではSSRガードを通す（プライベートIP・ループバック・リンクローカル・
  クラウドメタデータへのアクセスを、リダイレクトの各ホップで遮断する）

> モックはネットワークへアクセスせず、入力URLのホスト名から機械的に
> タイトルと本文を組み立てる。上記のルールは同じように適用されるため、
> `http://` や URL 形式でない文字列を入力するとエラーになる。

### クイズ生成（`quiz-generation`）

- 1問は **4択**。正解の番号は 0〜3
- 各問題は 問題文 / 選択肢4つ / 正解番号 / 解説 / 出典の抜粋（200文字以内）を持つ
- 1回の生成で **1〜5問**。モックは常に3問
- これらは生成元（モック / LLM）を問わず、生成時に検証される

### 出題（`/attempt/[id]`）

- 1問ずつ出題する。進捗（2 / 3）を表示する
- **正解と解説は回答前のクライアントに渡さない**。回答後のレスポンスで初めて渡る
- 回答すると即座に採点し、正誤・正解・解説を表示してから次へ進む
- 出題順どおりにしか回答できない
- 同じ問題には二度回答できない
- 全問回答した時点で自動的に終了し、スコアが確定する
  （「終了する」という操作は存在しない）

### 結果（`/attempt/[id]/result`）

- スコア（正答数 / 出題数）と全問の振り返り（設問・自分の回答・正解・解説）
- **完了していない挑戦の振り返りは取得できない**
- 出典のタイトルとURLを表示する

## 4. ダッシュボード（`/dashboard`）

学習状況を確認し、各一覧画面へ入る画面。**表示データはすべてモック**（後述）。

問題そのものの一覧はここには置かない。件数と入口だけを示し、
実際の一覧は `/quizzes` と `/review` に分ける。ダッシュボードが
長くなりすぎるのを避け、「見る画面」と「操作する画面」を分けるため。

### 構成

**1. サマリー統計**（カード2枚）

| 項目 | 内容 |
|---|---|
| 作成したクイズ | これまでに生成した問題の総数 |
| 通算正答率 | 全回答に占める正解の割合。回答数も併記する |

正答率は保存値ではなく、回答数と正解数から**常に導出する**。

**2. 一覧への入口**（カード2枚。件数付きのリンク）

| リンク先 | 表示する件数 |
|---|---|
| `/quizzes` 問題一覧 | 作成した問題の総数 |
| `/review` 復習待ち | 間違えたままの問題の数 |

復習待ちが0件のときもリンクは出す（「復習待ちはありません」と表示する）。
入口が消えると、どこにあった機能なのか分からなくなるため。

**3. 学習の記録（芝生）**

GitHub のコントリビューショングラフに相当する表示。

- **当月を1枚のカレンダー状のマス目で表示**し、`‹` `›` で前後の月に切り替える
- 保持するのは当月を含む **直近13ヶ月**。範囲の端ではボタンを無効化する
- マスの濃さは、その日の回答数に応じた **0〜4の5段階**
  （0問 / 1〜2問 / 3〜4問 / 5〜7問 / 8問以上）
- 今日のマスには枠線を付ける
- ヘッダーに **通算学習日数**（1問以上答えた日の総数）、
  グリッド下にその月の学習日数を表示する
- 全月分のデータをサーバーから渡しているため、月の切り替えで再取得は発生しない
- **「今日」の判定と月グリッドの組み立てはサーバー側で確定させる**。
  クライアントで日付を取り直すとサーバー描画と食い違うため

**4. 直近の挑戦**（5件）

各行に 記事タイトル / ドメイン / スコア / 正答率 / 相対日時（「3時間前」）。

各行から**その記事の復習**へ入れるようにする（第5章を参照）。

> **現時点では結果画面への遷移も記事単位の復習も付けていない。**
> モックの `attemptId` は実在せず、遷移させても「見つかりません」になるため。
> 挑戦がDBに保存されるようになった時点で両方の導線を追加する。

**5. 空状態**

クイズを1問も作っておらず、挑戦も0件の場合に表示する。
`lib/constants.ts` の `MOCK_DASHBOARD_IS_EMPTY` を `true` にすると確認できる。

### モックデータの性質

- **全ユーザー共通**。ユーザーIDは参照していないので誰が見ても同じ内容になる
- シードを固定した擬似乱数で生成するため、リクエストのたびに数字は変わらない
- 芝生の合計回答数と、サマリーの「回答数」は一致させている
  （別々に決めると「芝生は埋まっているのに回答数が少ない」といった矛盾が起きるため）

## 5. 復習

**未実装。** クイズと回答がDBに保存されていないと成立しないため、
`quiz-catalog` の実装が前提になる（第8章を参照）。この章は決定した仕様であり、
実装時にここを起点とする。

### 復習対象の定義

**最後に答えて間違えたままの問題**（`Quiz.lastIsCorrect === false`）。

| `lastIsCorrect` | 意味 | 復習対象 |
|---|---|---|
| `false` | 最後に答えて間違えた | **対象** |
| `true` | 最後に答えて正解した | 対象外 |
| `null` | まだ一度も答えていない | 対象外 |

- 未回答の問題は復習ではなく、**問題一覧（`/quizzes`）から解く**
- 復習で正解すると `lastIsCorrect` が `true` になり、復習対象から外れる
- 復習でまた間違えれば `false` のまま残る

> **既知の弱点**：一度間違えた問題をまぐれで正解すると、二度と出てこない。
> 「最後に答えてからN日経過した問題も対象にする」あるいは間隔反復（SRS）で
> 補える。`Quiz.lastAnsweredAt` は既にあるため前者は列追加なしで実現できる。
> 今回はスキーマ当初の設計どおり単純な定義を採用し、この点は保留とする。

### 出題モード

`Attempt.mode` に持たせる。どのモードでも出題・回答・採点の流れは同じで、
違うのは「出題対象の選び方」だけ。

| モード | 出題対象 | 入口 |
|---|---|---|
| `normal` | 生成したてのクイズ全問 | URL入力からの生成 |
| `review_all` | 全体の復習対象から、選んだ問数まで | `/review` の「復習を始める」 |
| `review_url_wrong` | その記事の復習対象すべて | 記事ごとの「間違えた問題を復習」 |
| `review_url_all` | その記事の全問 | 記事ごとの「全問もう一度」 |
| `review_selected` | 一覧で選んだ問題 | `/quizzes` の「選んだ問題を解く」 |

> スキーマの `Attempt.mode` のコメントは `"normal" | "review_all" | "review_url"` の
> 3つになっている。上記に合わせて更新が必要（第8章）。

### 出題対象の確定

- セッション開始時に出題対象を確定し、`AttemptQuiz` にスナップショットとして保存する
- **復習中に正解して `lastIsCorrect` が変わっても、そのセッションの出題内容は変わらない**
- 復習セッションも通常と同じ `Attempt`。「出題順どおりにしか回答できない」
  「同じ問題に二度回答できない」「全問回答した時点で終了」といったルールは共通

### 復習を始める動線

**1. 復習待ち一覧（`/review`）から**

- 復習対象の問題を一覧表示する
- 開始前に**問数を選ぶ**（10問 / 20問 / すべて）。対象が多いときに終わりが
  見えないと着手しづらいため。選んだ数を超える分は次回に回る
- 優先順は **最後に答えてから古い順**（`lastAnsweredAt` の昇順）。
  放置されている問題から先に出す
- 対象が0件のときは「復習待ちはありません」と表示し、開始ボタンは出さない

**2. 結果画面（`/attempt/[id]/result`）から**

- その回に間違えた問題だけをその場でもう一度解く
- 記憶が新しいうちに復習できるのが狙い
- 対象はその回の誤答のみ（最大でも出題数）なので**問数は選ばせず全問出す**
- 全問正解だった場合はボタンを出さない

**3. 記事（URL）単位で**

同じ記事から作った問題をまとめて解き直す。2つの導線を出す。

| ボタン | モード | 対象が0件のとき |
|---|---|---|
| 間違えた問題を復習 | `review_url_wrong` | ボタンを出さない |
| 全問もう一度 | `review_url_all` | 常に出せる |

対象は記事あたり数問なので**問数は選ばせず全問出す**。

置き場所は、ダッシュボードの「直近の挑戦」の各行と、`/quizzes` を
記事で絞り込んだときの見出し。

### 問題一覧（`/quizzes`）

作成した問題を**1問単位で**並べる画面。復習待ち一覧とは別画面。

- 各行に 問題文 / 出典記事 / 状態（正解済み・間違えた・未回答）
- **絞り込み**：状態（正解済み / 間違えた / 未回答）、記事（URL）
- **選択して解き直す**：チェックした問題だけを集めて出題する（`review_selected`）
- 並び順は作成日時の新しい順を既定とする

スキーマが「クイズ（1問単位のエンティティ。このアプリの真の主役）」と
位置づけているとおり、この画面が問題そのものへの入口になる。

> **`/review` との重複について。**
> `/quizzes` は状態で「間違えた」に絞り込めるため、`/review` は
> その絞り込みを適用した状態とほぼ同じ内容になる。別画面にするのは
> 復習への導線を短くするためで、**一覧の描画は同じコンポーネントを使い、
> 絞り込み条件と開始ボタンだけを変える**方針とする。二重実装を避けるため。

### 復習の結果

通常の挑戦と同じ結果画面（`/attempt/[id]/result`）を使う。
スコアの母数は復習で出した問数になる。

## 6. ヘッダー

`(app)` 配下の全画面に表示する。`sticky` でスクロールに追従する。

- 左: ロゴ（🧠 QuizStack）。ホームへのリンク
- 右: ユーザーメニュー。アバター（名前の1文字）と名前をクリックすると開き、
  ユーザー名とメールアドレスの確認・**ダッシュボードへの移動**・ログアウトができる。
  狭い画面では名前を隠しアバターのみ

ヘッダーにナビゲーションリンクは並べない。画面間の移動はユーザーメニューから行う。

### 組み立て方

ヘッダーとユーザーメニューは3者を `app/(app)/layout.tsx` で組み合わせて作る。

| 部品 | 置き場所 | 持つもの |
|---|---|---|
| `AppHeader` | `components/organisms/` | ロゴと、右側のスロット |
| `UserMenu` | `components/organisms/` | アバター・名前・メールの表示と、項目のスロット |
| `LogoutMenuItem` | `modules/user/components/` | ログアウト項目だけ |

**ナビゲーション項目（ダッシュボードへのリンク）はレイアウトが持つ。**
モジュールに置くと、認証のモジュールが画面遷移まで抱えることになるため。

## 7. 設計上の決まりごと

### レイヤー

各モジュールは `domain` / `use-cases` / `infrastructure` / `presentation` / `api` に分かれ、
依存は必ず外から内へ向く。`domain` は他のどの層も import しない。

- **`domain/entities`** — ドメインのルールを**エンティティ自身が持つ**。
  不変条件は生成時（`create` / `of` / `start` など）に検証し、
  それを通らないインスタンスは存在できないようにする
- **`domain/rules`** — 副作用のない純粋関数
- **`domain/ports`** — 外部との接点のインターフェース
- **`use-cases`** — 取得 → エンティティに委譲 → 保存、の調整のみ。判断はしない
- **`infrastructure`** — ポートの実装。差し替え可能
- **`presentation`** — Server Action（`'use server'`）
- **`api`** — RSC から呼ぶ読み取り。画面向けの形に詰め替える

### モジュール境界

公開口は用途で3つに分かれる。

| 入口 | 使う側 | 中身 |
|---|---|---|
| `index.ts` | サーバー（RSC・他モジュールのサーバーコード） | ユースケース・`api/`・コンテナ |
| `actions.ts` | `'use client'` なコンポーネント | Server Action だけ |
| `components/<name>.tsx` | 画面（直接パスで import） | UIコンポーネント |

- `'use client'` から `index.ts` を import してはいけない。サーバー専用の依存
  （DIコンテナ経由の Prisma など）がブラウザ側のバンドルに引き込まれ、ビルドが壊れる
- コンポーネントを `index.ts` に載せないのも同じ理由。直接パスで import する

**モジュールは画面共通のナビゲーションUIを持たない。** 共通の器は
`components/organisms/` に置き、モジュールは自分の関心事の部品だけを提供して、
両者を結び付けるのは `app/` のレイアウトの役割とする。

### DI

- ポートと実装の結び付けは各モジュールの `container.ts` の1箇所だけ
- モックを本実装に差し替えるときは **bind 先を変えるだけ**で済むようにする
- 全モジュールのコンテナは `lib/container.ts` で束ねる

### エラー

- Server Action は例外を throw せず、必ず `ActionResult<T>`（成功/失敗の判別共用体）で返す
- `ErrorCode` とユーザー向け文言は `lib/errors.ts` に集約する

### その他

- TypeScript strict、`any` 禁止
- Server Component がデフォルト。`'use client'` は必要な末端のみ

### 復習より先に `quiz-catalog` が要る

第5章の仕様はすべて「過去に作ったクイズと、その最終回答の正誤」に依存している。
現状は `Quiz` を永続化しておらず `Attempt` もメモリ保持のため、**復習は一行も
実装できない**。着手順は次のとおり。

1. `quiz-catalog` を新設し、生成したクイズを `Quiz` として保存する
2. `AttemptStore` をDB実装に差し替え、回答時に `Quiz.lastIsCorrect` を更新する
3. 復習の出題モードと `/review` `/quizzes` を実装する
4. `DashboardRepository` をDB集計の実装に差し替え、ダッシュボードのモックを解消する

3 と 4 は独立しているため順序を入れ替えてよい。1 と 2 は前提。

### `quiz-generation` の domain 層が越境 import している

`domain/ports/quiz-generator.ts` が `content-extraction` の `ExtractedContent` に
依存しており、最も守られるべき層が他モジュールに繋がっている。

抽出結果は永続化しない方針が確定しているため独立モジュールとして立てる根拠は弱く、
`content-extraction` を `quiz-generation` に統合すれば解消する。未対応。
